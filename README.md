   ## Why this project

Real-world data is rarely clean: missing values, values stored in the wrong format, extreme values and duplicates can silently distort analyses and machine-learning models. This project builds a reproducible data quality pipeline on a public dataset (77,679 Paris listings from Inside Airbnb). It profiles the data, validates it against explicit rules, cleans what can be fixed safely, quarantines doubtful rows instead of deleting them, and measures how well the rules detect known errors. It is a learning project: the rules and thresholds are provisional, and the main goal is a transparent, tested and reproducible method rather than a production tool.

Requirements: Python 3.10+ and Java 17+ (needed by Spark).

```bash
git clone https://github.com/ayabenmeftah84-rgb/data-quality-pipeline.git
cd data-quality-pipeline
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# Download listings.csv.gz (Paris) from https://insideairbnb.com/get-the-data/
mkdir -p data/raw   # then put the file in data/raw/

python src/run_pipeline.py
```

The pipeline runs three steps in order: profiling (`src/profile_data.py`), cleaning with quarantine (`src/clean_data.py`) and validation before/after cleaning (`src/validate_data.py`). On the full Paris file it takes about 4m12.831s on a laptop (Spark in local mode). Use `--steps clean validate` to run only some steps. Results are written to `reports/`.

 ## Data cleaning

The raw file has 77,679 listings and 90 columns. The cleaning script (`src/clean_data.py`) makes these decisions:

- **12 columns that are 100 % empty are dropped** (list in `reports/cleaning_log.json`).
- **`price` is converted from text (e.g. `$226.75`) to a number.** Listings without a price are kept and flagged with `price_missing`, because a missing price is not necessarily an error.
- **53 review scores equal to 0 are set to missing.** This is an assumption: a score of 0 is treated as "no score".
- **184 `host_about` values made only of digits are set to missing**, because they may be phone numbers (personal data).
- No duplicate `id` was found.

### Quarantine: extreme values pending review

48 listings (0.06 % of the data) are moved to a separate quarantine file instead of being deleted. They are **extreme values awaiting verification**, not confirmed errors. Each one keeps the reason why it was set aside:

| Rule | Threshold | Listings |
|---|---|---|
| Price too high | > $10,000 per night | 31 |
| Bedrooms too high | > 15 | 11 |
| Bathrooms too high | > 10 | 5 |
| Beds too high | > 20 | 4 |

A listing can break several rules, so the counts add up to more than 48. Manual inspection shows a mix: some rows look like real errors (for example 33 bedrooms with a single bed, or a studio priced above $50,000 per night), while others are coherent and plausibly real (large properties with many beds, bedrooms and bathrooms, or high-end homes). The thresholds are provisional and set at the top of `clean_data.py`. The quarantine files are not committed to Git (see `.gitignore`), but they can be regenerated by running the script.

## Error injection experiment

To measure what the rules can actually detect, `src/evaluate_detection.py` injects known errors into a copy of the raw data and runs the cleaning again. For each of 9 error types, 500 errors are injected into distinct rows that were valid in the original data (seed 42). An error counts as detected if the row is quarantined for the expected reason, if the corrupted value is set to missing, or if the duplicate is removed.

| Injected error | Rows injected | Detected | Detection rate |
|---|---|---|---|
| Price multiplied by 100 | 500 | 440 | 88.0 % |
| Price made negative | 500 | 500 | 100.0 % |
| Extra digit typed in beds (2 becomes 23) | 500 | 258 | 51.6 % |
| Review rating set to 7.5 | 500 | 500 | 100.0 % |
| first_review and last_review swapped | 500 | 500 | 100.0 % |
| Latitude shifted by 5 degrees (about 550 km) | 500 | 500 | 100.0 % |
| Latitude shifted by 0.05 degrees (about 5 km) | 500 | 0 | 0.0 % |
| Free text replaced by a phone number | 500 | 500 | 100.0 % |
| Row duplicated (same id) | 500 | 500 | 100.0 % |

**How to read these results**

- Errors that break a hard constraint are all detected: negative prices, ratings above 5, inverted dates, coordinates far from Paris, phone numbers in a text field and duplicated ids.
- Errors that stay inside the allowed range are missed. A price multiplied by 100 goes unnoticed when the original price was $100 or less (12 % of cases here), because the result stays under the $10,000 threshold. An extra digit in `beds` goes unnoticed when the original value was 1 (48.4 % of cases), because 13 is under the limit of 20. A GPS shift of about 5 km is never detected, because the whole shift stays inside the bounding box around Paris.
- This shows the limit of fixed thresholds and motivates rules that compare columns with each other (for example price per bedroom, or beds against bedrooms) or that use the local distribution of the data.

**Caveats**

- The errors are synthetic and were chosen by the author. The overall rate (3,698 of 4,500, 82.2 %) depends on this mix, so the rates per error type are more meaningful.
- The experiment measures detection only. It does not measure false alarms on legitimate extreme values: some of the 48 quarantined rows of the real data may be genuine large or luxury properties. That no other row was quarantined during the experiment is expected, because the rules are applied row by row.
- Only one random sample (seed 42) was used.

## Limitations and future work

- **Subtle errors are missed.** The error injection experiment shows that fixed thresholds miss errors that look plausible, such as small GPS shifts or a typo in a small number of beds. ## Results

Great Expectations validates the same 18 rules before and after cleaning (`src/validate_data.py`). "Before" uses the raw data with a minimal typing only (no value is corrected). "After" uses the cleaned data.

| Rule | Before cleaning | After cleaning |
|---|---|---|
| `id` not null | PASS | PASS |
| `id` unique | PASS | PASS |
| `price` > 0 and <= 10,000 | FAIL (31 rows, 0.064 %) | PASS |
| `price` present in at least 95 % of rows | FAIL (29,277 rows, 37.69 %) | FAIL (29,269 rows, 37.70 %) |
| `beds` <= 20 | FAIL (4 rows) | PASS |
| `bedrooms` <= 15 | FAIL (11 rows) | PASS |
| `bathrooms` <= 10 | FAIL (5 rows) | PASS |
| 7 `review_scores_*` columns in ]0, 5] | FAIL (3 to 9 rows per column) | PASS |
| `last_review` >= `first_review` | PASS | PASS |
| `latitude` inside the Paris bounding box | PASS | PASS |
| `longitude` inside the Paris bounding box | PASS | PASS |
| `host_about` not made only of digits | FAIL (184 rows, 0.514 %) | PASS |

**Summary.** 5 of 18 rules pass before cleaning and 17 of 18 after. The data goes from 77,679 to 77,631 rows (48 quarantined) and from 90 to 80 columns (12 empty columns dropped, 2 indicator columns added: `price_missing` and `flag_minimum_nights_gt_365`). Detailed reports are in `reports/`.

**How to read these results**

- The rules used for validation are the same as those applied during cleaning, so the "After" column mainly confirms that the cleaning applies the rules correctly. It does not prove that the data is free of errors.
- Apart from missing prices (37.7 %) and `host_about` (0.5 %), every failed rule concerns fewer than 0.1 % of rows. The most significant quality issues of this dataset are the 12 empty columns and the missing prices.
- One rule still fails after cleaning by design: missing prices are not imputed.
- **Fixed thresholds instead of consistency rules.** Quarantine relies on fixed limits (price, beds, bedrooms, bathrooms). Some legitimate large or luxury properties are quarantined, and some errors could pass unnoticed. A better approach would use **cross-column consistency rules**, for example comparing beds, bedrooms and guest capacity, or checking the price per bedroom or per guest.
- **Missing prices are not imputed.** About 38 % of listings have no price. They are kept and flagged rather than filled with guesses, so the rule "price present in at least 95 % of rows" still fails after cleaning.
- **Zero review scores are an assumption.** Treating 0 as "no score" should be checked against the data documentation.
- **Approximate geographic check.** Coordinates are validated against a rough bounding box around Paris.
- **One data snapshot, run locally.** The pipeline was tested on a single Inside Airbnb file, with Spark in local mode on one machine.
- **Orchestration with Airflow and richer quality metrics** (for example data lineage or drift monitoring) are planned but not implemented yet.
